- **Splitting a bound module strands its goal binding and orphans every descendant — FIXED for two instances, OPEN as a recurring shape.** Goal↔code bindings name a path. When a bound file `X.rs` is split into `X/mod.rs` plus siblings, the binding keeps naming `X.rs`, which no longer exists: `scripts/binding-audit.mjs` then reports one stale binding *and* every new descendant as unbound. Measured 2026-08-29 at 36 unbound source files and 2 stale bindings. Both stale ones were exactly this: `crates/ackplane-bridge/src/administration.rs` split into `administration/{mod,export,policy,purge,recovery,snapshot}.rs` (commit `1db004ab`), leaving all six unbound; and `crates/ackplane-server/src/work_command_store/model.rs` split into `model/{mod,digest,validation}.rs`, whose descendants had since been bound separately, leaving only an obsolete entry. Repaired by binding the six descendants to the goal their predecessor held and unbinding both dead paths — 0 stale bindings, 30 unbound. **Why it will happen again:** the `rust-module-length` control actively tells agents to split any module over 450 non-test lines, and 8 modules are over it right now, so the repository's own guidance drives the exact edit that breaks binding. The two controls are in tension and nothing connects them. What is not fixed: no guard notices a split, so the next one strands silently. A rename-aware check (a binding whose path vanished in the same commit that added a same-named directory is a split, not a deletion) would close it. The remaining 30 unbound files are mostly genuinely-new code whose governing goal is a judgement call, deliberately reported rather than mass-bound on a guess — binding a file to a too-broad goal makes conformance answer "covered" when a narrower clause should have governed, which is worse than being visibly unbound.
- **`binding-audit` is checkout-relative but the ledger is repository-shared, so "stale" depends on which worktree you run it from — OPEN, and dangerous to act on blindly.** Bindings live in the per-repository `spec.db` that every linked worktree shares, but the audit resolves each bound path against the working tree it happens to run in. Measured 2026-08-29 against one unchanged database: run from a checkout at `origin/main` it reported **4 stale bindings**; run from the worktree holding the unmerged branch that adds those files, **0**. The four were `crates/ackplane-mcp/src/{main,server,tools,endpoint}.rs`, correctly bound for a branch that had not landed yet. Impact: in a fleet (22 worktrees attached here) every binding for in-flight work reads as stale from every other worktree, and the obvious remediation — unbind what the audit calls stale — would silently strip governance from another agent's unmerged code, which then lands ungoverned and invisible to conformance. Not fixed this run. Anyone acting on a stale report must first confirm the path is absent from `origin/main` as well as from the local checkout; a `--base <ref>` option that judged staleness against a ref rather than the current tree would remove the footgun.
