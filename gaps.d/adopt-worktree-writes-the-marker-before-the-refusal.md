- **`worktree-owner.mjs --adopt-worktree` mutates the ownership marker even when it goes on to refuse the adopt.** Observed live: I ran `node scripts/worktree-owner.mjs --adopt-worktree` against `MindLeak.worktrees/claim-work-feature-ad258f7e` (a worktree owned, per its marker, by a different session than mine) intending to reconcile PR #842's conflict myself. The command correctly refused — `checkActiveClaimOnBranch` found task `task:786184c53f09`, a fresh, live, non-expired claim by a third session explicitly scoped to fix that exact conflict — and exited 4 as designed. But the on-disk marker (`.git/worktrees/claim-work-feature-ad258f7e/lodestar-owner`) had already been overwritten with *my* session id before that refusal ran, and stayed overwritten after the exit. Root cause: `ownershipVerdict()` (`scripts/worktree-owner.mjs`) returns `{action: "record", reason: "deliberate handover"}` unconditionally whenever `adopt` is true (line ~43), with no knowledge yet of whether an active claim exists; `checkWorktreeOwnership()` writes the marker as a side effect of that verdict (line ~301) immediately, at CLI line ~319 — strictly before `checkActiveClaimOnBranch`/`activeClaimRefusal` run at lines ~333-341 and can call `process.exit(4)`. The ordering is backwards: the write that should only happen on a *successful, uncontested* adopt happens on every adopt attempt, contested or not. Impact: the worktree's ownership record no longer matches either the original owning session or the session actually holding the live Lodestar claim; the next real commit from the legitimate claim-holder would itself be refused by the very same script ("owned by another agent"), naming *my* session as the blocking owner — the exact collision this file exists to prevent, caused by the tool meant to prevent it. Recovered by hand: restored the marker file to its original recorded value (`7c1f9a3e5b2d48f0a6e94c7d0b3f5182`) immediately after discovering the mutation, before anyone else's commit could be affected. Not fixed this run (docs/coordination session, no code changes made): the fix is to compute the active-claim check *before* deciding the verdict, e.g. have `checkWorktreeOwnership` accept the already-resolved `activeClaim` (or refuse to write when `adopt` requests a branch with a live foreign claim), so a refused adopt is provably a no-op on disk, not just a nonzero exit code operators are trusted to notice and manually undo.
