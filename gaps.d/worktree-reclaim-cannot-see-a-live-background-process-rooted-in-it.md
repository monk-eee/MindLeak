- **Worktree reclaim has no way to see a long-lived background process rooted in the worktree it is about to remove — only a build lock and a dirty tree.** Observed live: `scripts/delivery-queue.mjs --watch`, started this session as a detached background process from `MindLeak.worktrees/docs-fixes-mindleak-repo-drift`, was killed mid-tick when that exact worktree was reclaimed by this repository's own automation while the watcher was still running inside it. `worktree-reclaim.mjs`'s existing pre-flight (`scripts/worktree-reclaim.mjs`) checks for a dirty tree and a build lock ("a build is running here") but has no concept of an arbitrary child process whose current working directory is the worktree about to be removed; the reclaim was, by its own rules, correct (the branch's PR had merged, the tree was clean, no build lock existed), so it proceeded and deleted the directory tree out from under the watcher. Symptom: the watcher's next `require`/spawn against its own script path failed with `MODULE_NOT_FOUND` and the process exited (code -1); `git worktree list` no longer shows the worktree at all (fully pruned, not just `.git`-unlinked). This is a distinct symptom of the same root cause already fixed for MindLeak/Lodestar's own storage resolution (`gaps.d`'s prior "stale workspace resolves to empty database" entry, closed by `fix(storage): refuse a workspace path that no longer exists`, commit `16179206`) — that fix covers the MCP client reconnect path specifically (`mindleak-storage::repository::resolve`), not an arbitrary long-lived Node.js process someone `cd`'d into a worktree and left running. Recovered by restarting the watcher rooted in the primary checkout (`C:\Users\lyndonswan\Repos\MindLeak`, never a linked worktree and therefore never a reclaim target) instead of a disposable worktree; a second, independently-started watcher elsewhere in the fleet had already picked up the queue in the interim, so no work stalled. Not fixed this run: either `worktree-reclaim.mjs` gains a check for live child processes rooted under the candidate path (platform-dependent and easy to get wrong), or the operational rule becomes "root persistent background daemons in the primary checkout, never a linked worktree" — documented here rather than enforced, since no mechanism currently makes that rule anything more than a convention an agent has to remember.
