- **A "missing field `node_id`" projection-rebuild error was reported against this stack in an earlier session, and does not reproduce from a clean `docker compose down -v && up -d --build`.** `crates/ackplane-server/src/projection/mod.rs` defines a `node_id: String` field on a projected node payload deserialized from stored ledger records (`crates/ackplane-server/src/projection/rebuild.rs`), so a "missing field" error there is consistent with a stored record predating that field, or a payload written by an older/incompatible build of this same branch during earlier manual testing against a persistent `ackplane-postgres-data` volume, not with anything reproducible against a fresh database. Confirmed by full teardown (`docker compose down -v`, which drops the named volume) and rebuild: `ackplane`'s and `bridge`'s logs show no such error, only an unrelated transient connection race (see the sibling fragment below). Not force-fixed into the Bridge-in-compose work that surfaced it, per that work's own acceptance criteria explicitly scoping this out; re-open only with a concrete reproduction against a fresh volume.
- **`ackplane` and `bridge` both transiently fail their first Postgres connection attempt on a fully fresh `docker compose up`, recovering via their own `restart: unless-stopped` policy within a few seconds.** Measured across two independent clean-slate (`down -v` then `up -d --build`) bring-ups: both services logged `"... connection closed with an error", "error":"db error"` (ackplane) / `could not connect to Ackplane read models: error connecting to server` (bridge) immediately after `migrate` reported `service_completed_successfully`, restarted (RestartCount 2 for each), and settled into `healthy` on a later attempt; `postgres`'s own container never restarted. Consistent with a brief window where `pg_isready` (postgres's healthcheck) and `migrate`'s own successful exit both report affirmatively slightly before Postgres is fully ready to accept a *fresh* connection from another client, on a completely new data directory. Self-heals via the existing restart policy every time observed. Left for later because it is pre-existing (affects `ackplane`, which this session did not touch, identically to `bridge`) and out of scope for the Bridge-specific task that surfaced it. A tighter remedy, if this proves more than cosmetic, would give `ackplane`/`bridge` their own `depends_on: postgres: condition: service_healthy` in addition to depending on `migrate`, rather than relying on `migrate`'s own healthy-postgres dependency to imply the database is universally ready for new connections by the time `migrate` exits.
