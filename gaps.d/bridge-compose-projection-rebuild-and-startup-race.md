- **A "missing field `node_id`" projection-rebuild error was reported against this stack in an earlier session, and does not reproduce from a clean `docker compose down -v && up -d --build`.** `crates/ackplane-server/src/projection/mod.rs` defines a `node_id: String` field on a projected node payload deserialized from stored ledger records (`crates/ackplane-server/src/projection/rebuild.rs`), so a "missing field" error there is consistent with a stored record predating that field, or a payload written by an older/incompatible build of this same branch during earlier manual testing against a persistent `ackplane-postgres-data` volume, not with anything reproducible against a fresh database. Confirmed by full teardown (`docker compose down -v`, which drops the named volume) and rebuild: `ackplane`'s and `bridge`'s logs show no such error, only an unrelated transient connection race (see the sibling fragment below). Not force-fixed into the Bridge-in-compose work that surfaced it, per that work's own acceptance criteria explicitly scoping this out; re-open only with a concrete reproduction against a fresh volume.
- **`ackplane` and `bridge` both transiently fail their first Postgres connection attempt on a fully fresh `docker compose up`, recovering via their own `restart: unless-stopped` policy within a few seconds -- MEASURED 2026-08-28, RESOLVED 2026-08-29 as a side effect of a different fix, RE-VERIFIED not to reproduce.** Originally measured across two independent clean-slate (`down -v` then `up -d --build`) bring-ups: both services logged `"... connection closed with an error", "error":"db error"` (ackplane) / `could not connect to Ackplane read models: error connecting to server` (bridge) immediately after `migrate` reported `service_completed_successfully`, restarted (RestartCount 2 for each), and settled into `healthy` on a later attempt; `postgres`'s own container never restarted. My own first-pass guess was a `pg_isready`-vs-actually-ready timing race, but a corrected fragment recorded in Lodestar knowledge for this same stack (bridge-bin-tests-interfere-in-the-shared-test-database, since corrected) named a more likely, *measured* cause worth checking first: `docker-compose.yml` never set Postgres's `max_connections`, leaving it at the default of 100, against a workload where `ackplane` and `bridge` each open one connection per store at startup (11 and 17 respectively, by that fragment's own count) -- a burst of simultaneous connection attempts at boot is a more specific, testable explanation than a bare readiness-timing guess, and matched the `SqlState(E53300)` ("sorry, too many clients already") that fragment measured directly via `pg_stat_activity` in a related context.
  **Update 2026-08-29:** `docker-compose.yml` now starts Postgres with `command: ["postgres", "-c", "max_connections=500"]` (landed for `the-postgres-connection-ceiling-fails-the-suite-misleadingly.md`, a separate fix for `cargo test --all` exhausting the same default-100 ceiling). Re-tested this exact scenario against that change: five independent clean-slate (`down -v` then `up -d --build`) bring-ups, `ackplane` and `bridge` both `RestartCount: 0` and zero `error`/`closed` log lines every time -- a full reversal of the original two-for-two reproduction. This is consistent with, but does not independently re-confirm, the connection-count theory above (no `pg_stat_activity` capture was taken this pass either, so this is still corroborating evidence, not a controlled isolation of the variable). Left open rather than deleted because five clean trials cannot rule out a race at a lower probability than this sample can detect, and because it was never isolated as a controlled experiment -- but the practical remedy this fragment was tracking (self-healing, low-severity, blocking nothing) now appears resolved as a side effect of unrelated work.
