- **`ProcessWorkerAdapter::terminate` (`crates/ackplane-supervisor/src/worker_adapter.rs`) can leak a zombie process on Unix.** It calls `child.kill()` and returns without a following `child.wait()`/`try_wait()`. `Child::kill` only sends the signal — it does not reap the process — and `std::process::Child`'s `Drop` impl does not call `wait` either (a well-known Rust stdlib gap, not specific to this crate), so on Linux/macOS the killed child's PID stays a zombie in the OS process table until this adapter's own owning process (the supervisor) eventually exits and `init`/the reaper cleans it up. A long-lived supervisor that starts and force-terminates many short-lived workers over its lifetime accumulates one zombie entry per termination. `observe()`'s `try_wait()` path does not have this problem: `try_wait` reaps on success, so a worker that exits on its own is collected correctly — only the explicit-kill path in `terminate()` is affected. Windows has no equivalent zombie-process concept (the `Child`'s process `HANDLE` is closed on `Drop` regardless), so this is Unix-only exposure, consistent with this repo's platform-agnostic-toolchain requirement not being violated by the *fix* itself, only by the current gap.
  Not fixed this run: the correct fix is a `child.wait()` (or `try_wait()` retried with a bound) after `kill()` in `terminate()`, but a meaningful regression test for "no zombie was left behind" needs OS process-table inspection (e.g. `libc::waitpid` with `WNOHANG` in a Unix-only test, or shelling out to `ps`), which is more than a one-line change and did not fit the time budget of the bug-hunt pass that found this. Left for a follow-up that adds the wait call plus a `#[cfg(unix)]` regression test asserting the process is reaped (not merely that `terminate()` returns `Ok`).
