- **The shared Postgres connection ceiling fails `cargo test --all` in a pattern that reads exactly like a semantic code break.** Measured 2026-08-28 while validating an unrelated client-side change: 16-17 tests failed across five unrelated `ackplane-server` modules at once — `projection`, `signing_keys`, `supervisor_store`, `telemetry_service`, `readiness`, `knowledge_store`, `service::directive_receipt`. Every one was `SqlState(E53300)` "sorry, too many clients already" raised at a `connect` call site. `ackplane-postgres-1` reported `max_connections = 100` with **104 connections already in use before the run began**, because several fleet sessions share it. Re-running the identical suite with `--test-threads=6` gave **564 passed, 0 failed**. Where: every DB-gated test in `crates/ackplane-server` opens its own connection and nothing bounds how many run at once. Impact: the failing *test names* never mention connections — only the panic body does — so the visible signal is "seven unrelated subsystems just broke", and an agent validating their own diff will go looking for a cause inside it. That is a real cost, not a cosmetic one; it nearly happened here. NOT fixed this run, and deliberately so: each available remedy is a decision rather than a patch. Capping test threads slows an already slow suite for everyone; raising `max_connections` spends shared memory on the whole fleet's behalf; introducing a pool changes what the tests actually exercise, and several of them assert connection-level behaviour. The suite is not broken — it passes with bounded parallelism. It is the failure *mode* that misleads.
