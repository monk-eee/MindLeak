- **A derived index table gets created away from the schema file, and loses the foreign key every sibling has.** Both planes independently shipped the same defect: MindLeak's `embeddings` (fixed, PR #785) and Lodestar's `knowledge_embeddings` (fixed, this change) were each built by an optional index pass calling `ensure_table` at runtime, rather than being declared in `schema.sql` beside the tables that do cascade. Observed in `crates/mindleak-core/src/embed.rs` and `crates/lodestar-core/src/embed.rs`, both carrying a comment justifying the placement — Lodestar's said "This module owns its table, so adding the index needs no schema migration" — and that same reasoning is what skipped the constraint in each case. Impact: MindLeak reached 48,502 orphaned rows and 142.1 MiB (74.3% of the table) before it was noticed; Lodestar was caught at zero only by luck of timing, since its decay prune had not yet reached an embedded lesson. Both are fixed, but nothing stops the next lazily-created table repeating it: there is no check that a table referencing another entity declares a foreign key onto it, and `ensure_table`-style runtime DDL is invisible to any review of `schema.sql`. Consider a test or audit that enumerates tables holding a `*_id` column naming another table and asserts a declared constraint.
