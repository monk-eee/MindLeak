- **CLOSED (2026-09-02), the "nothing stops a branch-local experiment" half, via PR #907/#909 (merged).** `ackplane-migrate --mark-shared` is a one-time, explicit provisioning action for whoever stands up a shared or persistent Postgres instance (never an ephemeral local or CI container). Once a database is marked, `migrate_locked` — the one chokepoint every store's `connect()` runs its migration DDL through — refuses any migration key without an explicit `ACKPLANE_MIGRATE_REVIEWED=1` acknowledgement, which should only be set after confirming the key via `migration-audit.mjs`. The actual refuse-or-apply decision (`shared_gate_refuses` in `crates/ackplane-server/src/migration_lock/mod.rs`) is a pure function, tested exhaustively without touching any live database — deliberately, since even a briefly-inserted marker row against this fleet's own shared `ackplane_test` risked refusing an unrelated concurrent migration for a reason that had nothing to do with it. **Still open, narrower than before:** the guard still cannot answer in a shallow clone, and repairing an already-poisoned ledger row still means mutating shared database state by hand — both unchanged by this fix, since neither is "can a branch-local experiment reach shared state at all", which is what this closes.

- **UPDATE (2026-08-30): a collision is now refused rather than silently skipped, which is the half of this that was actually dangerous.** Every update above treats a burned key as an accounting problem. It was worse than that. `ackplane_schema_migrations` recorded only `migration_key` and `applied_at`, and `migrate_locked` skipped the DDL and returned `Ok(())` whenever the key was already present — so a migration whose number a concurrent branch had applied **never ran its own SQL**, the schema silently lacked whatever it creates, and the failure surfaced much later somewhere unrelated. `migration_lock.rs`'s own key comments record it happening: key 44 collided "with a different session's migration under the _same_ key", which `scripts/migration-audit.mjs` cannot detect precisely because the branch's own source _does_ account for that key — only the content can tell the two apart. The ledger now records a content digest alongside the key, and a key held under different content fails with a message naming both digests and pointing at `--next`. Editing an already-applied migration file reaches the same refusal, which is what [ADR-0063](../docs/adr/0063-a-migration-may-tidy-the-past-never-the-present.md) already asks for. Re-running the identical migration still skips, unchanged. A row written before the digest column has no digest and says nothing about which migration wrote it, so it is skipped exactly as this database has always skipped it and its digest adopted — never assumed, since reconstructing it would assert a fact the ledger never held. **Still open, and unchanged:** nothing stops a branch-local experiment applying a key to shared state in the first place. Detection is complete for both shapes at the runtime guard — a key applied with no committed source, and a key applied under different content — but prevention still needs the reviewed isolation or gating policy this fragment has asked for since 2026-08-22. (The _audit tool_'s coverage of the second shape came later; see the 2026-09-02 update above.)
