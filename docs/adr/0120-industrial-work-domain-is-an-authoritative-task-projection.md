# ADR-0120: Industrial Work is an authoritative task projection, not a mirrored board

## Context

ADR-0105 makes Work and Board Doctor a required Industrial Bridge capability: a human must be able to see tasks, allocation, leases, overlap, stalls, durable waits, and review state across an enrolled fleet. The currently shipped Bridge Agents view is intentionally narrower. It reads `delegated_claims`, so it can answer who holds a live lease, in which repository, on which branch, and under what declared scope. It cannot answer what the task is for, whether it is blocked or waiting, which review/evidence state applies, why it stalled, or whether no row means no work, no publication, or a stale projection.

The absence is structural. `delegated_claims` is a correct authority for one resource: a lease keyed by tenant, repository, and task id. It has no title, acceptance, parent relationship, lifecycle event, wait, checkpoint, review, or conformance reference. Treating that table as a task board would make a missing claim look like a finished or healthy task and would force the Bridge to infer state that Ackplane never received.

Local Lodestar already has a rich task lifecycle, but ADR-0096 deliberately did not federate it. Its decision 1 moved only ownership into Ackplane and kept Local goal definitions, acceptance text, task threads, evidence bundles, and conformance verdicts local. That was the right first boundary: a claim adapter must not silently become a wholesale `spec.db` replication protocol. It also explicitly left the larger question open. A server-owned Work domain is that larger question and needs its own decision before a task table, browser cache, or Bridge command creates an accidental second authority.

## Decision

**An Industrial repository has one optional Ackplane-authoritative Work namespace. It is an append-only task-event domain with a checked projection; it is not a replication of Lodestar's `spec.db`, a claims-only dashboard, or a browser-owned cache. A task belongs to either the Local or Industrial namespace at a time, never both.**

1. **Authority mode is explicit and pinned per task namespace.** A Local task remains a Lodestar record governed by the repository-local Intent Plane. An Industrial task is created in Ackplane's tenant/repository Work namespace and is governed by Ackplane's PostgreSQL transaction, event log, and projection. A client does not select Local or Industrial authority on each mutation based on reachability. Moving a task between namespaces is an explicit, auditable migration with an old-to-new reference and never a background mirror or best-effort sync.

2. **An Industrial task has a stable identity and bounded workflow record.** Its immutable identity is `(tenant_id, repository_id, work_id)`; `work_id` is opaque and server-assigned. The initial event records a bounded title and acceptance, optional parent work reference, goal and Constitution identifiers plus immutable content digests only, declared path and symbol scope, creation actor, and source/protocol version. It never carries a Goal or Constitution definition/body. Subsequent events may name allocation, a typed wait, checkpoint/evidence references, review/conformance references, or a terminal disposition. The versioned schema assigns a fixed maximum byte or element count to every accepted field and rejects an over-limit payload before persistence. Ackplane stores only the bounded values and references needed to operate the Industrial task; it never accepts a raw Local database, arbitrary thread transcript, terminal log, source excerpt, credential, or unbounded prompt as task content.

3. **The event log is authoritative and the current task is a verifiable projection.** Industrial Work events are immutable, ordered within a tenant/repository stream, and carry the actor/principal, recorded time, expected prior version, idempotency identity, operation-specific payload digest, and resulting version. PostgreSQL allocates the event position, persists the event, and updates the Work projection in one transaction under ADR-0086's repository-stream discipline. The current projection records an explicit lifecycle state: `open`, `claimed`, `waiting`, `paused`, `blocked`, `in_review`, `completed`, or `abandoned`. It also records parentage, current scope, bounded wait/checkpoint/review references, and the source event position. Replaying the events must reproduce the projection. A mismatch makes the affected Work projection unavailable to reads and visible as repair work; a route handler never silently repairs or guesses it. The trigger, concurrency, and operator workflow for projection repair are implementation or operational-decision work, not an implicit browser behavior.

4. **ClaimStore remains the only lease authority.** A Work projection may display an owner, branch, lease expiry, lapse count, and declared scope, but it derives them from the Ackplane claim grant and its history. Claim, renew, release, and recover use the existing authoritative ClaimStore compare-and-swap semantics from ADR-0096. When one accepted operation changes both a Work task and its claim, the same PostgreSQL transaction locks the claim row, appends its history and the Work event, updates both projections, records the linked receipt references, and commits them together. The Work domain does not mint a second lease column, accept a browser's claimed state as truth, or infer ownership from a heartbeat.

5. **Existing claims remain legible but are not silently invented into tasks.** A legacy `delegated_claims` row with no corresponding Industrial Work record remains a claims-only record. Bridge labels it as such and reports the missing task projection; it never fabricates a title, acceptance, wait, review state, or terminal outcome from absence. This ADR does not authorize Local-to-Industrial task import. A later migration decision must define the source reference, explicitly selected bounded fields, Local archive/closure behavior, task-id mapping, actor authorization, and idempotent receipt before any Local task can become a new Industrial Work record. It must not bulk-copy `spec.db`, synthesize history, or mark an imported task healthy merely because it has a lease.

6. **Freshness and absence are part of every Work answer.** A Work list, detail, overlap, stalled, or Board Doctor response identifies tenant and repository scope, task/claim stream positions, projection time, and a publication state such as `current`, `lagging`, `claims_only`, `not_published`, or `unavailable`. A repository with no Work projection is not reported as a clean empty board. Tenant and repository authorization occurs before any task, claim, event, or reference lookup, so a cross-tenant request is refused without revealing whether an id exists.

7. **The first Bridge Work surface is read-only and bounded.** It exposes versioned read resources for a paged/filterable task list, task detail and event history, declared scope/overlap, stalled and waiting work, and Board Doctor findings. Lists follow ADR-0112: bounded pagination or cursoring chosen for their growth pattern, allow-listed sorting and filters, and stable totals/cursors. Board Doctor is a deterministic diagnostic projection over Work, ClaimStore, and publication freshness; it may name missing task publication, stale projection, impossible state/lease combinations, unresolved waits, and scope overlap, but it never mutates a task.

8. **Commands are deliberately deferred.** ADR-0105's promise that an authorized Bridge operator can create and route work is roadmap intent, not a present mutation authorization: when that command exists, it creates or routes an Industrial Work record rather than proxying a Local task through Bridge. This ADR does not authorize Bridge creation, routing, assignment, release, pause, resume, answer, review, completion, abandonment, or any generic task mutation endpoint. Existing node-signed claim RPCs and ADR-0111's narrowly approved recovery keep their current contracts. A future command contract must separately define principal authorization, task-version compare-and-swap, idempotency, confirmation where consequential, receipt/evidence links, and typed local-supervisor directives for any device-bound effect. It cannot use a browser-to-SQL shortcut, raw MCP forwarding, a shell command, or an untyped state patch.

9. **Compatibility expands beside the legacy claim read model.** The initial schema adds Work events and projections without changing the meaning of existing claim rows or existing Agents endpoints. Readers distinguish Industrial Work, legacy claims-only, and absent publication during rollout. Writes use expand, backfill/import, verify, then contract migrations; a schema or protocol version is retained with every event so a later reader can refuse an unsupported interpretation rather than guessing.

## Consequences

- The Industrial Work and Board Doctor implementation can build a real task model without copying Local Lodestar storage or making the Bridge a decorative claims table. It now has a concrete list of authority, event, projection, freshness, and compatibility properties to test.
- An operator sees honest partial state during rollout. A live claim with no Industrial task record is a visible `claims_only` condition, not an empty task board or a made-up task.
- Ackplane gains a new durable domain with task-event and projection tables, versioned read contracts, migration discipline, and projection repair checks. That is intentionally more than a Fleet query, because Work needs lifecycle and provenance rather than only a lease.
- Local-first operation remains complete. Local Lodestar tasks remain local unless a repository explicitly chooses an audited migration into Industrial authority; an Ackplane outage never silently creates a Local substitute for an Industrial task.
- Future task controls have a safe substrate but are not automatically enabled. Authorization, human delegation, and supervisor-control decisions remain separate gates, especially for operations that change local worker state or terminal task disposition.

## Rejected alternatives

**Copy `spec.db` or mirror every Local task event into PostgreSQL.** Rejected because it creates two writable task stores, leaks Local-only evidence and thread content into the server by default, and turns conflict resolution into an accidental synchronization problem. A deliberate Industrial task is a new authoritative record, not a replica.

**Treat `delegated_claims` as the Industrial task model.** Rejected because a lease has no acceptance, wait, review, completion, parentage, or publication-freshness semantics. A missing lease cannot distinguish no work from expired work, unreported work, or a broken projection.

**Let the browser cache own task state and reconcile it later.** Rejected because a browser is ephemeral, has no authoritative transaction boundary with ClaimStore, and cannot safely settle concurrent state or tenant access. Browser state is a view of the bounded server projection only.

**Proxy every Local Lodestar task mutation through Bridge.** Rejected because it violates ADR-0096's Local boundary, makes offline Local task work depend on a server, and makes a UI transport path look like a task authority.

**Expose all Work controls with the first read model.** Rejected because reading a task does not grant authority to create, assign, pause, answer, or complete it. Each command needs its own reviewed principal, state-race, idempotency, receipt, and local-effect semantics before it can leave a read-only surface.
