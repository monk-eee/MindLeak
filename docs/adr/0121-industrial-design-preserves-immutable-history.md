# ADR-0121: Industrial Design preserves immutable history, not a mutable current snapshot

## Context

The current Ackplane Constitution projection is intentionally read-only: an enrolled node publishes a signed complete snapshot of its repository-local Lodestar Constitution, and Ackplane never edits that local source. Its current schema has one row per tenant/repository. A new publish upserts that row, deletes every projected clause, and inserts the latest clause set. That is enough for the Fleet page to render the active Constitution, but it erases the historical version that explains why a policy, work assignment, review, or materialization decision was valid when it occurred.

The Local Design Board already treats history as load-bearing. A design item remains durable through proposed, accepted, rejected, deferred, retired, and superseded states. Acceptance and materialization are separate records; materialization plans are reviewed, revisioned, and linked to resulting goals, tasks, and constraints. Those Local records are not safe to copy wholesale into Ackplane: they include repository-local workflow and may refer to Local-only task, thread, evidence, or filesystem state. A browser must not scrape an ADR file or a developer database and call that Industrial history.

ADR-0105 requires a Bridge Design Board that exposes published design/ADR discovery, current and historical Constitution versions, proposal and decision state, materialization plans and revisions, and links into Work, Evidence, and policy. The existing active-snapshot projection cannot meet that contract honestly. A new Design domain also cannot become a second writable authority for a Local design item, or a shortcut that lets a browser adopt, reject, or materialize local work without the human and authorization controls those actions require.

## Decision

**Industrial Design has two explicitly separate record classes: immutable signed Constitution publications from a repository-local source, and optional Ackplane-authoritative Industrial design/materialization records. This extends ADR-0106's read-only projection with historical retention; it does not claim the existing current-snapshot table already provided it. Neither class is a mirror of `spec.db`, and Bridge reads both through checked, tenant-scoped projections.**

1. **Every published Constitution version is immutable and retained.** A signed publication identifies `(tenant_id, repository_id, version_id)` and carries a protocol/schema version, publication time, status, bounded clause snapshot, source path/reference digest, and payload digest. The pair `(tenant_id, repository_id, version_id)` is unique. Retrying an identical publication returns the durable original; publishing the same identity with a different digest is refused. A new publication never updates or deletes an earlier publication or its clauses. The active version is a separate checked projection/pointer, not a destructive replacement of history.

2. **Ackplane remains a projection, never the editor of a Local Constitution.** Constitution publications originate from an enrolled repository node through an authenticated, versioned contract. Ackplane verifies the publisher and stores the resulting immutable projection; it never reads a repository filesystem, invokes Local MCP, rewrites an ADR, or executes Local `accept_design`, `reject_design`, `retire_design`, or materialization verbs. A published version can state that its Local source was accepted, rejected, retired, or superseded, but the server records that source fact rather than deciding it on the source's behalf.

3. **Industrial design records are a separate authority for Industrial-only decisions.** An Industrial design record has an opaque `(tenant_id, repository_id, design_id)` identity, bounded title and summary, source/protocol version, lifecycle state, immutable references to Constitution publications and Work/Evidence records, and an append-only decision history. The schema enforces that `(tenant_id, repository_id, design_id)` is unique and that every Constitution/Work/Evidence reference names an existing record in the same tenant and repository. It may represent a server-owned proposal, acceptance, rejection, deferral, retirement, supersession, or reviewed materialization decision only when a future typed command authorizes that state transition. It does not reuse a Local design id as a writable alias, does not import a Local database row by default, and does not cause a Local Design Board row to change.

4. **Materialization is revisioned and referential, not a task-generation side effect.** An Industrial materialization plan/revision records its actor/principal, idempotency identity, rationale, target Constitution publication, bounded references to resulting Industrial Work records or goals, and a payload digest. An identical retry returns the original revision; a changed revision appends a new immutable record. The domain never treats model output, browser cache, or a task title match as a reviewed plan. A Local design/materialization chain and an Industrial chain never interleave: an Industrial revision cannot supersede, repromote, or replace a Local promotion, and an immutable publication reference is lineage evidence rather than a writable alias. It never copies Local task acceptance, thread content, evidence bundles, or constraints into an Industrial record without a separate explicit migration contract.

5. **Bounded fields and references are enforced at the schema boundary.** The versioned contract defines maximum byte or element limits for titles, summaries, clauses, plans, references, and pagination. It rejects credentials, arbitrary terminal output, raw source excerpts, unbounded prompt text, and arbitrary database payloads. Constitution/design references are opaque ids, approved paths, version ids, and content digests; they are not an excuse to inline a Local Constitution or Local design history into the server.

6. **Bridge Design reads expose history and uncertainty honestly.** Versioned read resources provide a bounded Design list, one design/detail history, Constitution version list/detail, materialization revisions, and links to referenced Work/Evidence/Constitution records. Every result identifies tenant/repository scope, active publication/version, source position or publication time, projection freshness, and an explicit state such as `current`, `historical`, `not_published`, `lagging`, `partial_history`, or `unavailable`. A tenant/repository authorization check happens before a design, version, clause, materialization, or reference lookup; an unauthorized caller cannot learn whether an id exists. A repository migrated from the current single-snapshot schema is marked `partial_history`: its active snapshot is preserved as an imported baseline, while earlier unpublished versions are never invented. If a Local-published Constitution and an Industrial design describe the same human subject, Bridge renders them as distinct source and Industrial records with their explicit immutable lineage reference; it never deduplicates them by title, path, or inferred similarity, and no display link makes either writable through the other.

7. **The first Bridge Design Board is read-only.** It may filter and page published or Industrial design records, inspect immutable version/materialization history, show retired or superseded state, and navigate to linked Work/Evidence/Constitution views. It does not adopt, reject, defer, retire, supersede, create, or materialize a design. Those commands require separately reviewed principal authorization, version compare-and-swap, idempotency, separation of duties, durable receipts, and any typed enrolled-node directive needed to affect a Local repository.

8. **Migration expands without rewriting history.** The implementation adds version-history and active-pointer/projection tables beside the current snapshot schema, imports each current active snapshot as one explicitly marked baseline publication, verifies the active view agrees with the old reader, then moves Bridge reads to the new projection. It does not manufacture older versions, mutate an existing publication's content, or drop the legacy tables until the checked migration is complete. A version or schema reader that cannot interpret a record refuses that record rather than guessing a current state.

## Consequences

- The Industrial Design Board can show exactly which Constitution version and materialization revision informed work without pretending the active snapshot is the whole design history.
- Existing signed Constitution publication remains a read-only local-source projection. Industrial Design creates an Ackplane authority only for deliberately Industrial decisions, not for a Local ADR or Design Board row.
- Ackplane needs immutable Constitution-version, clause-version, Industrial-design-event, and materialization-revision records plus checked active/list/detail projections. The schema and protocol are follow-on implementation work, not created by this ADR.
- A first migration gives operators useful current state without falsifying historical completeness. `partial_history` is a product truth, not an error state to hide.
- Future Design commands are safer because they have a stable version, principal, idempotency, and receipt substrate. They remain unavailable until their own authorization decision lands.

## Rejected alternatives

**Keep only the latest mutable Constitution snapshot.** Rejected because a current clause set cannot explain the historical policy basis for a task, review, materialization, or receipt, and it makes immutable Local versions appear to have been overwritten by the server.

**Copy `spec.db` or mirror every Local design event into Ackplane.** Rejected because it creates two writable design authorities, leaks Local-only thread/evidence content by default, and makes synchronization conflicts the design model.

**Let Bridge parse ADR files or query Local MCP on demand.** Rejected because a browser/server cannot treat one developer's filesystem or local process as a tenant-wide authority, and an unavailable workstation would make history disappear.

**Use a browser cache as the Design history store.** Rejected because it has no durable transaction, tenant guard, immutable revision semantics, or reliable recovery path. Browser state is a view of the server projection only.

**Expose adoption and materialization with the first read API.** Rejected because reading a design does not authorize a consequential lifecycle change. Each command needs a separately reviewed identity, state-race, separation-of-duties, receipt, and Local-effect contract.
